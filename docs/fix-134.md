# fix-134: GameStatAggregator 증분 집계 전환

## 문제

증분 sync(30분 스케줄)에서 신규 게임이 1건이라도 있으면 `aggregate(userId, platform)`이 호출되어
**Game 테이블 전체**(최대 수만 건)를 DB에서 읽은 뒤 stat 테이블 3개를 전부 delete → 재계산 → saveAll 하는 구조였다.

```
30분 스케줄 → 신규 게임 5건 저장 → gameRepository.findByUserIdAndPlatform() (50,000건 로드)
  → dailyStatRepository.deleteByUserIdAndPlatform() + saveAll()
  → colorStatRepository.deleteByUserIdAndPlatform() + saveAll()
  → firstMoveStatRepository.deleteByUserIdAndPlatform() + saveAll()
```

## 원인

`aggregate()`가 `(userId, platform)` 만 받아 전체 재계산하는 방식으로 설계되어 있었고,
Worker에서 이미 `saveAll()` 반환값(`List<Game> saved`)을 가지고 있었음에도 이를 집계에 넘기지 않았다.

## 수정 내용

### 1. Domain 레포지토리 — findByKey 메서드 추가

- `UserDailyGameStatRepository`: `findByUserIdAndPlatformAndDate()`
- `UserColorStatRepository`: `findByUserIdAndPlatformAndTimeClassAndColor()`
- `UserFirstMoveStatRepository`: `findByUserIdAndPlatformAndTimeClassAndColorAndMove()`

### 2. JPA 레포지토리 — Spring Data 파생 쿼리 추가 (동일 메서드명 3개)

### 3. Repository 구현체 — 위임 메서드 추가 (3개)

### 4. GameStatAggregator — `aggregateIncremental()` 추가

```java
public void aggregateIncremental(Long userId, OAuthPlatForm platform, List<Game> newGames)
```

- 신규 게임만 받아 기존 stat 행을 찾아 카운터를 더함 (없으면 신규 생성)
- DB 접근: Game 전체 로드 없음, 신규 게임의 unique key 수만큼만 stat 조회
- 기존 `aggregate()` (full recompute)는 초기 전체 수집(`processFullSync`) 및 긴급 재집계용으로 유지

### 5. LichessGameSyncWorker — `processIncremental()` 수정

- `totalNewlySaved: int` → `allNewlySaved: List<Game>` 로 변경하여 저장된 게임 누적
- `aggregate()` → `aggregateIncremental(userId, platform, allNewlySaved)` 호출

### 6. ChessComGameSyncWorker — 수정

- `fetchAndSave()`: `void` → `List<Game>` 반환
- `processParallel()`: `void` → `List<Game>` 반환 (CompletableFuture<List<Game>> 사용)
- `processSequential()`: `void` → `List<Game>` 반환
- `process()`: 반환된 게임 목록으로 `aggregateIncremental()` 호출

### 7. user_monthly_rating_stat 테이블 신설 (rating-history O(N²) 쿼리 대체)

**문제**: `getRatingHistory()`가 `Game` 테이블에서 `(timeClass, year, month)` 그룹별 마지막 게임을 찾는
코릴레이티드 서브쿼리를 사용 → YEAR()/MONTH() 함수 사용으로 인덱스 미사용, O(N²) 성능

**해결**: 월별 레이팅 스냅샷을 별도 테이블에 사전 집계

신규 파일:
- `chessmate-domain/.../stat/UserMonthlyRatingStat.java`
- `chessmate-domain/.../stat/UserMonthlyRatingStatRepository.java`
- `chessmate-infra-persistence/.../entity/UserMonthlyRatingStatJpaEntity.java`
  - unique constraint: `(user_id, platform, time_class, year, month)`
- `chessmate-infra-persistence/.../jpaRepository/UserMonthlyRatingStatJpaRepository.java`
- `chessmate-infra-persistence/.../mapper/UserMonthlyRatingStatMapper.java`
- `chessmate-infra-persistence/.../repositoryImpl/UserMonthlyRatingStatRepositoryImpl.java`

### 8. GameStatAggregator — monthly rating 집계 추가

- `isAnyStatEmpty()`: `monthlyRatingStatRepository.existsByUserIdAndPlatform()` 체크 추가
- `aggregate()`: `computeMonthlyRatingStat()` 호출 추가
  - 전체 게임을 `(timeClass, year, month)` 키로 그룹화
  - 그룹당 `playedAt` 최신 게임의 `rating`을 저장
  - delete + saveAll
- `aggregateIncremental()`: `incrementMonthlyRatingStat()` 호출 추가
  - 신규 게임을 동일 키로 그룹화
  - 기존 행이 있으면 rating 교체(신규 게임이 항상 더 최신), 없으면 신규 INSERT

### 9. Worker 디스패치 로직 수정 (긴급 복구 자동화)

기존 문제: `isAnyStatEmpty() == true && newGames.isEmpty()` 이면 `aggregateIncremental(emptyList)`
→ rated.isEmpty() 조기 반환 → stat 테이블이 빈 채로 방치

```java
// 수정 전
if (!allNewlySaved.isEmpty() || statAggregator.isAnyStatEmpty(...)) {
    statAggregator.aggregateIncremental(..., allNewlySaved);
}

// 수정 후
if (statAggregator.isAnyStatEmpty(...)) {
    statAggregator.aggregate(...);          // 전체 재집계 (Game 테이블 기반)
} else if (!allNewlySaved.isEmpty()) {
    statAggregator.aggregateIncremental(..., allNewlySaved);  // 증분
}
```

적용 파일: `LichessGameSyncWorker.processIncremental()`, `ChessComGameSyncWorker.process()`

**배포 시 자동 백필 흐름**: `user_monthly_rating_stat` 테이블이 비어있음
→ `isAnyStatEmpty()` true → 다음 스케줄 실행 시 `aggregate()` 호출 → Game 테이블 기반 전체 재집계

### 10. StatService.getRatingHistory() — 신규 테이블로 교체

```java
// 수정 전: 코릴레이티드 서브쿼리
gameRepository.findMonthlyLastRating(userId, platform, timeClass, since)

// 수정 후: 단순 인덱스 조회
monthlyRatingStatRepository.findByUserIdAndPlatform(userId, platform)
    .stream()
    .filter(timeClass 및 12개월 범위 필터)
```

`GameRepository` 의존성 제거, `LocalDateTime` import 제거

## 성능 비교

| | 수정 전 | 수정 후 |
|---|---|---|
| 증분 집계 DB 읽기 | Game 전체 (N건) | 신규 게임 unique key 수 (≈ stat 조회 3~10건) |
| 증분 집계 stat 쓰기 | delete + saveAll 전체 | 변경된 행만 saveAll |
| 증분 집계 복잡도 | O(전체 게임 수) | O(신규 게임 수) |
| rating-history 쿼리 | O(N²) 코릴레이티드 서브쿼리 | O(1) 인덱스 조회 (user_id, platform) |
