# fix/#124 — Lichess `getUser()` 비인증 호출 + 429 backoff 미구현 버그 수정

## 발견 경위

프로덕션 배치 로그에서 수 시간에 걸쳐 반복 발생한 패턴:

```
[Lichess API] Authorization 헤더: Not present
429 Too Many Requests: {"error":"Too many requests. Try again later."}
at PerfStatFetcher.fetchLichess(PerfStatFetcher.java:57)
```

OAuth 토큰이 있는 유저(userId=146 skibidigamer6767)도 게임 수집은
`Authorization: Present`인데, 바로 이어지는 `getUser()` 호출은
`Authorization: Not present`로 찍히는 것이 핵심 단서였다.

---

## 버그 1 — `LichessApi.getUser()`에 Authorization 헤더 없음

### 원인

`LichessApi.getUser()`의 시그니처에 `@RequestHeader` 파라미터가 아예 없어서
OAuth 토큰 보유 유저도 항상 비인증 공개 API(20 req/min)로 호출됐다.

```java
// 수정 전
@GetExchange("/api/user/{username}")
LichessAccountDto getUser(@PathVariable("username") String username);
```

`LichessGameSyncWorker`는 `tokenStore`에서 토큰을 꺼내 `getGames()`에는 넘기지만,
`PerfStatFetcher.fetch()`에 토큰을 전달하는 경로가 없었다.

### 영향

- Lichess 비인증 한도: **20 req/min** (전체 엔드포인트 합산)
- 스케줄러가 초당 1건씩 job을 처리하면서 게임 수집 + `getUser()` 호출이 동시에 발생
- 토큰 유무와 무관하게 모든 `getUser()` 호출이 비인증 한도를 소모 → 반복 429

### 수정

**`LichessApi.java`**
```java
// 수정 후
@GetExchange("/api/user/{username}")
LichessAccountDto getUser(
    @RequestHeader(value = "Authorization", required = false) String authHeader,
    @PathVariable("username") String username
);
```

**`PerfStatFetcher.java`** — `fetch()` 시그니처에 `accessToken` 추가
```java
public void fetch(Long userId, OAuthPlatForm platform, String username, String accessToken)

private void fetchLichess(Long userId, String username, String accessToken) {
    String authHeader = accessToken != null ? "Bearer " + accessToken : null;
    LichessAccountDto account = fetchUserWithRetry(userId, username, authHeader);
    ...
}
```

**`LichessGameSyncWorker.java`** — 두 호출 지점 모두 `accessToken` 전달
```java
// processFullSync
perfStatFetcher.fetch(userId, OAuthPlatForm.LICHESS, username, accessToken);

// processIncremental
perfStatFetcher.fetch(userId, OAuthPlatForm.LICHESS, username, accessToken);
```

## 버그 2 — 429 발생 시 backoff/retry 없음

### 원인

```java
// 수정 전 — catch → log.error → 다음 job으로 넘어감
try {
    fetchLichess(userId, username);
} catch (Exception e) {
    log.error("[PerfStatFetcher] 페프 스탯 조회 실패 ...", e.getMessage(), e);
}
```

429를 일반 Exception과 동일하게 처리해 즉시 포기했다.
재시도 없이 다음 job이 바로 실행되므로 429가 연쇄적으로 발생했다.

### 수정

**`PerfStatFetcher.java`** — `callWithRetry()` 추가 (Supplier 기반 범용 retry)

```java
private static final int  MAX_RETRIES         = 5;
private static final long BASE_BACKOFF_MS      = 60_000L;
private static final long BACKOFF_INCREMENT_MS = 5_000L;

private <T> T callWithRetry(Supplier<T> call, String context) {
    for (int attempt = 0; attempt <= MAX_RETRIES; attempt++) {
        try {
            return call.get();
        } catch (HttpClientErrorException.TooManyRequests e) {
            if (attempt < MAX_RETRIES) {
                long wait = BASE_BACKOFF_MS + (long) attempt * BACKOFF_INCREMENT_MS;
                log.warn("[PerfStatFetcher] 429 수신, {}ms 대기 후 재시도 {} attempt={}/{}",
                    wait, context, attempt + 1, MAX_RETRIES);
                try {
                    Thread.sleep(wait);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("Backoff sleep interrupted", ie);
                }
            } else {
                log.warn("[PerfStatFetcher] 429 재시도 소진, 이번 사이클 수집 생략 {}", context);
                throw e;
            }
        }
    }
    throw new IllegalStateException("unreachable");
}
```

Lichess, Chess.com 모두 동일한 `callWithRetry()`를 사용:
```java
// fetchLichess
LichessAccountDto account = callWithRetry(
    () -> lichessApi.getUser(authHeader, username), "userId=" + userId);

// fetchChesscom
ChesscomPlayerStatsResponse statsResponse = callWithRetry(
    () -> chesscomApi.getPlayerStats(username), "userId=" + userId);
```

- 429 수신 시 60초 + attempt×5초 대기 후 최대 5회 재시도 (최대 대기: 80초)
- 재시도 소진 시 `log.warn` 후 skip → 외부 catch가 `log.error`로 기록
- `InterruptedException` 발생 시 interrupt 플래그 복원 후 `RuntimeException`으로 변환

## 코드 리뷰 후 추가 수정 (2026-04-22)

fix/#124 구현 후 코드 리뷰에서 5개 문제 추가 발견 및 수정.

### 문제 1 — `@Transactional` 범위 안에서 `Thread.sleep()` 호출 [심각]

**파일**: `PerfStatFetcher.java`

`fetch()`가 `@Transactional`로 선언되어 있어, 429 수신 시 60초(BASE_BACKOFF_MS 기준) 슬립하는 동안 DB 커넥션을 점유했다.
다수 유저가 동시에 429를 받으면 커넥션 풀이 고갈되는 구조였다.

```java
// 수정 전
@Transactional
public void fetch(...) { ... }

// 수정 후 — @Transactional 제거
// JPA Repository 메서드는 각자 트랜잭션을 보유하므로 기본 안전성 유지
public void fetch(...) { ... }
```

### 문제 2 — `InterruptedException` 발생 시 `TooManyRequests`로 변환 [중간]

**파일**: `PerfStatFetcher.java` — `callWithRetry()`

슬립 중 인터럽트가 걸리면 `TooManyRequests`(원래 429 예외)를 던져서 인터럽트 원인이 감춰졌다.
상위 `catch (Exception e)`가 이를 "perf stat 조회 실패"로 기록하고 삼겨버렸다.

```java
// 수정 전
} catch (InterruptedException ie) {
    Thread.currentThread().interrupt();
    throw e;  // TooManyRequests를 던짐 — 인터럽트 이유 소실

// 수정 후
} catch (InterruptedException ie) {
    Thread.currentThread().interrupt();
    throw new RuntimeException("Backoff sleep interrupted", ie);  // 원인 보존
}
```

### 문제 3 — `processIncremental` `last.createdAt()` NPE [중간]

**파일**: `LichessGameSyncWorker.java`

`games.getLast().createdAt()`에 null 방어가 없었다.
`toSave` 리스트에는 `createdAt != null` 필터가 있지만, `games`(원본)의 마지막 요소에는 없었다.
`processFullSync`는 `OptionalLong`으로 방어했는데 `processIncremental`은 누락됐다.

```java
// 수정 전
LichessGamesDto last = games.getLast();
since = last.createdAt() + 1L;  // createdAt null → NPE

// 수정 후
LichessGamesDto last = games.getLast();
if (last.createdAt() == null || last.createdAt() <= 0) {
    log.warn("[LichessWorker] 증분 수집 마지막 게임 createdAt 없음 — 수집 종료 userId={}", userId);
    break;
}
since = last.createdAt() + 1L;
```
